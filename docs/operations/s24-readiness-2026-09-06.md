## Installation and reconnection findings

1. **One bundled artifact fails its integrity pin.** The digest for
   `single_instance.py` in the [S24 installer](../../Sandbox/S24/install_s24.sh)
   differs from both the bundled file and its Git HEAD content. The other three
   pins match. All four bundled broker artifacts match their
   `Sandbox/Configuration` counterparts. The installer stops at the mismatch.
2. **Reconnection depends on completed enrollment.** The
   [phone agent](../../Sandbox/S24/device_agent.py) requires initial enrollment
   before operation. Its network retries apply to an enrolled agent. The kit
   does not install through a browser visit.
3. **A lost successful heartbeat response can stop the agent.** The
   [client](../../Sandbox/S24/broker_client.py) retries an identical signed
   envelope, while the [heartbeat handler](../../Dashboard/Current/api/device-heartbeat.js)
   rejects an already committed sequence or request identifier. That response
   becomes an authentication error and can terminate the agent. The existing
   mocked-disconnect test does not establish recovery after a server commit
   followed by response loss.
4. **Restart behavior remains unverified on the phone.** The installer creates
   startup configuration only after enrollment and a signed heartbeat. Its
   documentation omits a Termux:Boot availability check. Five seconds of process
   survival does not prove reboot recovery or continued operation under Android
   background restrictions.

## Dashboard and identity findings

- [The current dashboard API](../../Dashboard/Current/api/jp-devices.js) derives
  `live` from `lastSeen` age without requiring a signed enrollment heartbeat.
- [The configuration dashboard](../../Sandbox/Configuration/dashboard/index.html)
  renders the stored `online` flag directly. Periodic refresh does not resolve
  stale or unverified source data.
- Uncommitted local dashboard edits associate browser visitor identifiers with
  the canonical phone. Such mappings are not hardware verification. Their
  presence in a working tree does not establish that they are deployed.
- [Broker attestation validation](../../Dashboard/Current/lib/broker.js) checks
  supplied Android metadata rather than validating a hardware attestation
  certificate chain. An initial `SM-S928` model constraint alone does not
  distinguish a particular handset.

## Validation and acceptance criteria

Local inspection passed **8 Python AST checks** and **4 JavaScript syntax
checks**. Artifact pin verification passed **3 of 4 checks**. These checks do
not establish physical-device readiness.

Before claiming an operational deployment, verify:

- Matching artifact pins and recovery from a committed heartbeat whose response
  is lost.
- Consistent dashboard distinction between stale records, browser activity, and
  a fresh authenticated phone heartbeat.
- Ordinary approved installation and signed enrollment on the actual S24.
- Sustained heartbeats, network reconnection, and reboot/background recovery.
- A `status-only` command acknowledged and completed by the phone itself.

A website visit is not installation approval or proof of a connected daemon.
